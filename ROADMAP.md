## 36. One reader for the blob batch output that check-duplicates and check-roadmap parse

`writeStagedFiles` in `scripts/check-duplicates.mjs` and `headRoadmap` in `scripts/check-roadmap.mjs` each parse `git cat-file --batch` output by hand: the `<sha> <type> <size>` header, the content of that size and the `missing` answer. Move the parsing into one function in `scripts/script-support.mjs` that takes the output buffer and returns each object's type and content, or `missing`, in input order, and use it from both. Test it with a found blob holding multi-byte text, a missing object and two blobs in one output.

## 35. npm run verify resumes from a named step

A step of `npm run verify` that fails for a reason outside the change, such as the GitNexus worker failing to start in `graph:check` straight after the test suite, means running the full suite again, or the remaining steps one by one by hand. Make `scripts/verify.mjs` take `--from <step>`, running `STEPS` from that step to the end and refusing a step `STEPS` does not hold with the list of steps, and make its failure line name the command that resumes from the failed step (`npm run verify -- --from graph:check`). Describe it in the `npm run verify` sentence of `AGENTS.md`. Test that `--from` runs only that step and those after it, that an unknown step is refused with the steps listed, and that the failure line names the resume command.

## 38. npm run field:trace names every surface that carries a result field

A request to confirm a result field across the server means checking by hand the MCP tool descriptions and output schemas in `src/tools.ts`, the CLI `--help` text in `src/cli/commands.ts`, the README command table, the code that sets the field and the tests that assert it. Add `scripts/field-trace.mjs`, run as `npm run field:trace -- <field>`, which reads the tracked files and prints, for that field, each MCP tool whose description or output schema names it, each CLI whose help names it, whether the README command table names it, each source line outside tests that sets it, and each test file that asserts it, and exits non-zero with the missing surfaces named when a tool or CLI that `src/cli/result-field-docs.test.ts` maps the field to does not document it. Describe it in `AGENTS.md`. Test the output for a field every surface carries and the failure for one a CLI's help leaves out.

## 39. A check refuses hand-written HTML parsing in src

HTML is converted only by libraries (`html-to-text` for text, `turndown` for Markdown); a regular expression that matches tags or character references in source code is a hand-written parser. Add `scripts/check-html-parsing.mjs`, run as `npm run html-parsing:check` in CI and in `npm run verify` beside the other quick checks, which reads every tracked `src/**/*.ts` file outside tests and fails, naming each file and line, on a regular expression literal or `new RegExp` string that matches an HTML tag (`<[^>`, `<\/`, `<br`, `<a\s`, `<style`, `<script` and the like) or a character reference (`&#`, `&(?:`, `&[A-Za-z`). Describe it in `AGENTS.md`. Test that it passes on the current tree, fails on a file holding `.replace(/<[^>]+>/g, ' ')` with that file and line named, and passes on a test file holding the same line.

## 40. npm run release:status reports whether a commit is pushed, passed CI on origin and is the build the linked CLIs run

A consumer asking whether a change is released and installed means checking by hand that the commit is on `origin/main`, that its CI run passed, and that the `gmail-*` links in `~/.local/bin` point at this checkout's `dist` built from that commit. Plain `gh run list` resolves to the `upstream` remote, so it lists another repository's runs. Add `scripts/release-status.mjs`, run as `npm run release:status -- [<rev>]` (`HEAD` when left out), which fetches `origin`, resolves the revision to a full hash, and prints one line each for: whether `origin/main` contains it; the conclusion of its CI runs on the `origin` repository, passed explicitly with `--repo` as `scripts/ci-watch.mjs` derives it from `origin`; and each CLI that `install-cli` links, naming where its link points and whether `dist` was built from that commit. Have `npm run build` (or `install-cli`) write the hash it built from into `dist`, so the script can compare it. Exit non-zero naming each part that fails. Describe it in `AGENTS.md`. Test it with a commit that is not on `origin/main`, with a CI run that failed, and with a link that points outside the checkout.

## 41. import-prompts skips a prompt whose file a commit on main names, so a prompt whose work lands without import is never added as new work

A peer session can send a prompt's request as a message, and its work then lands without the prompt ever passing through `ROADMAP.md`. `scripts/import-prompts.mjs` skips a prompt only when its `Source:` line is or was in `ROADMAP.md`, so such a prompt (`gmail-alternative-parts.md` is one: `alternatives` is in the code, yet its Source line has never been in the roadmap) is imported as new work. Have the importer also skip a prompt whose file name a commit message on `main` carries as a `Prompt: <file>` token, found with `git log -F --grep`, and describe the token in `AGENTS.md` beside the import command so a commit that carries out a prompt directly names it. The commit on `main` that adds this item carries `Prompt: gmail-alternative-parts.md`, so that prompt is the first one recorded this way. Test that a prompt named by such a commit is skipped, that a prompt named only in an unrelated commit's prose without the token is still imported, and that the importer stays idempotent; check on the live repository that the importer and item 42's list both leave `gmail-alternative-parts.md` out.

## 42. npm run prompts:pending lists the gmail prompts neither imported nor named by a commit, and the SessionStart hook puts that list in a new session's context

A session that loses a peer's request (an editor restart drops the conversation) has to find the prompt file by hand among dozens in the prompts directory. Add `scripts/prompts-pending.mjs`, run as `npm run prompts:pending -- <prompts-dir>`, which reuses `importPrompts`' rules (and item 41's `Prompt:` token) without writing anything and prints each `gmail-*.md` prompt that is neither imported nor named by such a commit, with its title line and modification time, or `no pending prompts`. With no argument the script reads `../figaro-pa-predecessor/docs/prompts` taken relative to the main checkout's root (so a linked worktree reads the same directory), held as one constant in the script; document that default in `AGENTS.md` beside the import command. Have the project's SessionStart hook run it with no argument and put its output in a new session's context when that directory exists, saying nothing when it does not. Test it with an imported prompt, a prompt named by a `Prompt:` commit, a pending prompt, the default directory read from a linked worktree, and a missing directory.

## 43. One body-part predicate in message-body.ts shared by walk and alternativesOf

`walk` and `alternativesOf` in `src/message-body.ts` each decide on their own which parts are body text (a `text/plain` or `text/html` part with no filename) and how an inline one is decoded, and `alternativesOf` falls back to `''` for a deferred part it finds in neither outcome map. If the two rules drift, an `alternatives` item can read `''` with no `error` where `body` and `htmlBody` read the part differently. Move the rule into one exported `isBodyPart(part)` used by both, and have `alternativesOf` read a part's text from the decoded segments `extractWithSegments` already produces, keyed by part, instead of decoding it again. The `resolveMessageBody` alternatives tests in `src/message-body.test.ts` already check one HTML part through both `htmlBody` and its item, and a named `text/html` part left out of its item and listed in `attachments`; add to that named-part test the assertion that `htmlBody` leaves it out too, and keep both tests passing through the change.

## 44. Each CLI's help has a Result fields section naming every field of its JSON output with its type and when it is present

A consumer checks from an installed CLI's own `--help` that a release still returns the result fields it reads, and it can rely on a field only where the help names it in a result section. The help of gmail-search, gmail-get-message, gmail-download-attachment, gmail-get-attachment-text, gmail-batch-fetch-window and gmail-create-draft has no such section: it names fields in running prose without types, and gmail-batch-fetch-window's help names the fields of each `messages/NNN.json` but none of the result it prints. Give each of these six commands' help in `src/cli/commands.ts` a `Result fields:` section, one `name (type): meaning` line per field of its JSON output, items of arrays as `name[].field` and nested objects as `name.field`, each line saying when the field is present (always, or the condition under which it is) and when it can be null. gmail-batch-fetch-window's section covers the result it prints (crossCheck and failures included), and its `messages/NNN.json` fields stay described as they are. The output itself does not change. Add a test that, for each of the six commands, runs it against the Gmail API mock in the cases that produce each optional field and compares the set of field paths in its JSON output with the set its `Result fields:` section names, failing on a field in either set but not the other. Describe the section in the CLI spec and README.
